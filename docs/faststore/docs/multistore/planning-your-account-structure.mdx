A multistore project built on a [FastStore monorepo](https://developers.vtex.com/docs/guides/faststore-monorepo-overview) can serve its markets in two ways: from one VTEX account, using [bindings](https://help.vtex.com/docs/tutorials/what-is-binding), or from one VTEX account per market. This choice sets how catalog, pricing, and promotions are managed, and it determines how many CMS instances, WebOps integrations, and app-version targets the project operates.

> ℹ️ In both models, the repository is organized by VTEX account: each key in [`faststore.json`](https://developers.vtex.com/docs/guides/faststore-monorepo-overview#faststorejson-file) is an account name that points to a project directory in the monorepo. Bindings don't appear in this file. They're configured on the VTEX account itself, so an account with several bindings still has a single entry in `faststore.json`.

This guide compares the two models and shows what each one means for the CMS, the WebOps integration, and the app versions installed in the account.

## Choosing the account structure

> ⚠️ Make this choice before implementation starts. Changing the account structure after markets are live means migrating catalog, content, and deployments.

The following table compares the two models:

| Model | How it works | Best for |
| --- | --- | --- |
| [Single account with bindings](#single-account-with-bindings) | One VTEX account serves several storefronts, each with its own domain bound to a [sales channel](https://help.vtex.com/en/docs/tutorials/how-trade-policies-work). The catalog is shared. Promotions and prices are account-wide and apply to every market at once. Logistics settings can differ by sales channel but are managed in the same account. | Markets that share a catalog and a centralized commercial operation, managed in a single VTEX Admin. |
| [Multiple accounts](#multiple-accounts) | Each market or brand runs its own VTEX account, with its own catalog, pricing, promotions, logistics, and back office. | Markets that need commercial and operational autonomy, often with a separate team and a separate VTEX Admin per market. |

> ⚠️ If promotions, prices, or the catalog must be managed independently per market, use separate accounts. Forcing markets with commercial autonomy into one account means that promotions and payment settings affect every market at once, which is an operational risk.

Each VTEX account has its own [CMS](https://developers.vtex.com/docs/guides/cms-for-faststore-storefronts), [FastStore WebOps](https://developers.vtex.com/docs/guides/faststore/webops-dashboard) integration, and installed app versions, so the number of accounts sets how many of each the project runs.

### Single account with bindings

The single-account model depends on the [Localization feature](https://developers.vtex.com/docs/guides/faststore/storefront-features-handling-internationalization-with-the-localization-feature). A binding connects one domain to one sales channel and one locale. The catalog is shared across the account. FastStore reads only the binding's default locale, so each language needs its own binding.

> ⚠️ The Localization feature is in Closed Beta and requires FastStore v4. To request access, open a ticket with [VTEX Support](https://help.vtex.com/docs/tutorials/opening-tickets-to-vtex-support).

The three account-level parts of the implementation work as follows:

- **CMS:** The account has one [CMS](https://developers.vtex.com/docs/guides/cms-for-faststore-storefronts) instance. With Localization enabled, editors manage storefront content per locale in that CMS.
- **WebOps:** One WebOps integration deploys the account's single project, and every binding of the account is served by the same deployment. Bindings are configured on the account through [VTEX Support](https://help.vtex.com/docs/tutorials/opening-tickets-to-vtex-support) and enabled in the project's `discovery.config.js`.
- **App versions:** VTEX IO apps, such as Intelligent Search, backend apps, and Admin apps, are installed once in that account.

### Multiple accounts

In the multiple accounts model, each market or brand is a separate VTEX account with its own domain, catalog, pricing, language, and currency.

The account-level parts of the implementation work as follows:

- **CMS:** Each account has its own CMS instance, so an editor in one market works only in that market's content. Pages, components, and media that should match across markets, such as global policies or campaign assets, are maintained in each account. Section schemas stay in the repository, and the CMS doesn't copy them between accounts, so you sync them to each account deliberately. For the commands and steps, see [Keeping CMS schema sync manual](https://developers.vtex.com/docs/guides/faststore/multi-store-managing-environments#keeping-cms-schema-sync-manual).
- **WebOps:** Each account has its own WebOps integration, so the accounts share one repository and deploy independently. See examples of monorepo layouts in [Monorepo use cases](https://developers.vtex.com/docs/guides/monorepo-use-cases). How testing and production environments map to branches is covered in [Managing environments](https://developers.vtex.com/docs/guides/faststore/multi-store-managing-environments).
- **App versions:** Updating each account by hand doesn't scale. Two features control app versions centrally, without requiring administrative access to each account:

  | Feature | What it does |
  | --- | --- |
  | [Sponsor Account](https://developers.vtex.com/docs/guides/vtex-io-documentation-sponsor-account) | A parent account that sponsors child accounts and determines which Edition App and policies they run. A sponsor of a sponsor isn't supported. |
  | [Edition App](https://developers.vtex.com/docs/guides/vtex-io-documentation-edition-app) | Defines which VTEX IO apps, and at which versions, are installed across every account linked to the sponsor. |

Together they keep every account on the same versions of core apps, such as Intelligent Search, backend apps, and Admin apps. Decide which account will be the sponsor before creating the others, because the hierarchy has one parent and can't be nested later.

[VTEX Support](https://help.vtex.com/docs/tutorials/opening-tickets-to-vtex-support) enables the sponsor and installs its Edition App in the accounts you request. For more information, see [Becoming a Sponsor Account](https://developers.vtex.com/docs/guides/vtex-io-documentation-becoming-a-sponsor-account).

> ℹ️ FastStore requires `vtex.edition-store@5.x` in every account of the project, including any testing accounts. Learn more in the [Before you begin](https://developers.vtex.com/docs/guides/faststore/go-live-before-you-begin) article of the Going live track.
