A FastStore multistore architecture is a project in which a brand operates several FastStore storefronts, for example, one per country or one per brand.

This track covers how to build a multistore architecture from a single [FastStore monorepo](https://developers.vtex.com/docs/guides/faststore-monorepo-overview), where every market reuses the same components, design tokens, and delivery pipeline. You'll learn what to share, what to keep local, and the order to follow when setting up the stores.

> ℹ️ You can also run each store as a separate FastStore project in its own repository. In that case, sharing components and design tokens requires extra effort, such as publishing them as a package. This track focuses on the monorepo, but the guidance on account structure, environments, and content governance applies to both approaches.

## Shared foundation and local control

A multistore architecture isn't an attempt to make every market identical. The goal is to draw a precise line between what is shared across stores and what stays local for each market.

The following table shows how each layer is typically divided between shared and local:

| Layer | Shared | Local |
| --- | --- | --- |
| Components and design system | Component library, design tokens, section schemas | Per-market overrides and market-specific sections |
| Delivery | Repository, continuous integration pipeline, release process | Deployment target account and branch |
| Content | Section schemas that must look the same everywhere | Pages, campaigns, and media per market |
| Commerce | Nothing by default. Sharing depends on the account structure, not on the repository. | Catalog, pricing, promotions, logistics, payments |

Components and the delivery pipeline are shared because duplicating them creates inconsistencies between stores. Commerce configuration stays local because it's the part that the business team of each market needs to control directly.

> ℹ️ This division is a common starting point, not a fixed rule. Adjust it to your markets, teams, and governance needs. For example, a market with a different release schedule can use a different production branch in [FastStore WebOps](https://developers.vtex.com/docs/guides/faststore/webops-dashboard) while still sharing the repository and pipeline with the other stores. Learn more in [Configuring production and preview branches in WebOps](https://developers.vtex.com/docs/guides/faststore/webops-configuring-production-and-preview-branches).

## Implementation path

> ℹ️ If a store already runs on Store Framework and wants to migrate to FastStore, read step 8 before you start, since part of the migration happens during development.

A multistore project with one VTEX account per market typically follows this order:

1. **Define the account structure.** Choose the model, set up the [Sponsor Account](https://developers.vtex.com/docs/guides/vtex-io-documentation-sponsor-account) and [Edition App](https://developers.vtex.com/docs/guides/vtex-io-documentation-edition-app), and, if you use them, create the testing accounts. See [Planning your account structure](https://developers.vtex.com/docs/guides/faststore/multistore-planning-your-account-structure) and [Managing environments](https://developers.vtex.com/docs/guides/faststore/multistore-managing-environments).

    > ℹ️ If you chose a [single account with bindings](https://developers.vtex.com/docs/guides/faststore/multistore-planning-your-account-structure#single-account-with-bindings), the project has one account, one entry in `faststore.json`, and one WebOps integration, so creating a project per account and sharing code across stores don't apply. Instead, set up the [Localization feature](https://developers.vtex.com/docs/guides/faststore/storefront-features-handling-internationalization-with-the-localization-feature) to serve each binding, and then follow the remaining steps for that account: connecting it to the repository, validating changes, and going live.

    The account structure comes first because the other areas follow from it. Each VTEX account has its own [CMS](https://developers.vtex.com/docs/guides/cms-for-faststore-storefronts) instance and WebOps integration, so the number of accounts determines how many CMS instances and deployment targets the project uses.

    > ⚠️ Changing the account structure after markets are live results in significantly more effort and costs than setting it up correctly from the start. Moving a market later means rebuilding its content and deployment target.
2. **Set up the monorepo.** Initialize the repository and its `faststore.json` file. See [FastStore monorepo](https://developers.vtex.com/docs/guides/faststore-monorepo-overview).
3. **Create a project for each account.** Use the `fsp create` command to add each store to the monorepo. See [Creating new projects](https://developers.vtex.com/docs/guides/monorepo-creating-new-projects) and the [Monorepo use cases](https://developers.vtex.com/docs/guides/monorepo-use-cases).
4. **Run the stores locally.** Start each store with `fsp dev` and, to run several stores at the same time, set a different proxy port for each one. See [Running projects locally](https://developers.vtex.com/docs/guides/monorepo-running-projects-locally).
5. **Organize the shared code.** Create the shared package and define the customization layers. See [Sharing code across stores](https://developers.vtex.com/docs/guides/faststore/multistore-sharing-code-across-stores).
6. **Connect each account to the repository.** Set up the [FastStore WebOps](https://developers.vtex.com/docs/guides/faststore/webops-dashboard) integration of each account, and map branches to the testing and production accounts. See [Mapping branches to accounts](https://developers.vtex.com/docs/guides/faststore/multistore-managing-environments#mapping-branches-to-accounts).
7. **Validate changes and sync content structure.** Set up the continuous integration pipeline and sync section schemas to each account manually. See [Validating changes before merge](https://developers.vtex.com/docs/guides/faststore/multistore-managing-environments#validating-changes-before-merge), [Keeping CMS schema sync manual](https://developers.vtex.com/docs/guides/faststore/multistore-managing-environments#keeping-cms-schema-sync-manual), and [CMS for FastStore storefronts](https://developers.vtex.com/docs/guides/cms-for-faststore-storefronts).
8. **Go live with each store.** Each account goes live separately, on its own domain, so repeat the process for every market:
    - For a new store, follow the [Going live](https://developers.vtex.com/docs/guides/faststore/go-live-overview) track. If it's the account's first FastStore go-live, VTEX Support must activate the CDN workflow for that account.
    - For a store that already runs on Store Framework, follow the [Migrating from Store Framework to FastStore](https://developers.vtex.com/docs/guides/migrating-store-framework-to-faststore) guide from [Step 4 - Setting up your testing domain](https://developers.vtex.com/docs/guides/migrating-store-framework-to-faststore#step-4-setting-up-your-testing-domain) onward. The earlier steps of that guide, which cover the testing account, the Edition App, and the store project, are already covered by steps 1 to 3 of this path. When the guide asks you to connect the FastStore project to the production account, connect the monorepo, as described in step 6.
