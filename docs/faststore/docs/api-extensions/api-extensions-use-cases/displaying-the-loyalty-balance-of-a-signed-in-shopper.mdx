This guide describes how to extend your storefront's account page so signed-in shoppers can see their current loyalty balance. Because this balance is personal data tied to one specific shopper, the resolver must authenticate as that shopper rather than as the store, so each shopper only ever sees their own points and never another shopper's.

> ℹ️ For instructions on declaring type definitions and resolvers, see [Extending API schemas](https://developers.vtex.com/docs/guides/faststore/api-extensions-extending-api-schema). For the reasoning behind the credentials used here, see [Authentication in API extensions](https://developers.vtex.com/docs/guides/faststore/api-extensions-authentication-in-api-extensions).

## Context

- Your store runs a loyalty program that awards points for each order.
- The balance is stored in a custom Master Data entity named `LoyaltyBalance`, with the acronym `LB`.
- You want to display the balance on the account page, so each shopper sees their own points.
- The balance is personal data, so no shopper may read another shopper's record.

For this guide, we'll use a fictional account example, `examplestore`. Replace it with your own account name.

## Before you begin

Configure the access control list (ACL) of the `LoyaltyBalance` entity in the VTEX Admin so that a shopper can read only their own document. The endpoint used in this guide delegates the authorization decision to that ACL, so an entity without an ACL remains open to every shopper.

## Step 1: Creating the type definitions

Before the API can return a shopper's loyalty balance, your store's GraphQL schema needs to know that this data exists and what shape it takes. This step declares a new `loyaltyBalance` query and the `LoyaltyBalance` type it returns. The resolver you'll create in [Step 3](#step-3---creating-the-resolver) is what actually fetches the data to fulfill this query.

1. Open your store's repository in a code editor of your preference.
2. In the `src/graphql/vtex/typeDefs` directory, create a file named `loyalty.graphql`.
3. In the `loyalty.graphql` file, add the following content:

```graphql src/graphql/vtex/typeDefs/loyalty.graphql
type LoyaltyBalance {
  """
  Points currently available to the shopper.
  """
  availablePoints: Int!

  """
  Date when the next batch of points expires, in ISO 8601 format.
  """
  nextExpirationDate: String
}

extend type Query {
  """
  Returns the loyalty balance of the signed-in shopper.
  """
  loyaltyBalance: LoyaltyBalance
    @cacheControl(scope: "private", sMaxAge: 0)
}
```

In this file, the following is declared:

- `type LoyaltyBalance` defines a new GraphQL object type with the two fields the account page needs: `availablePoints` (required, hence `Int!`) and `nextExpirationDate` (optional, since a shopper with no expiring points has none to report). The triple-quoted comments above each field become that field's description in your API's schema.
- `extend type Query` adds a new root-level query, `loyaltyBalance`, to your store's existing GraphQL schema, without modifying any query that already exists. This is what makes `loyaltyBalance` queryable from a component later, once a resolver is registered for it.
- Notice that the query takes no arguments: the shopper's identity comes from the request, not from the caller, so there is no email or user ID to pass. The `@cacheControl` directive keeps the response out of shared caches. 

## Step 2: Creating the authentication helper

The resolver you'll write in [Step 3](#step-3---creating-the-resolver) needs to prove it's acting on behalf of the signed-in shopper, not the store. To do that, it needs the shopper's session token, which VTEX stores in a cookie on every authenticated request. This step creates a small helper that extracts that token from the request and fails fast, with a clear error, if the shopper isn't actually signed in, so the resolver itself doesn't have to deal with cookie parsing or missing-session edge cases.

1. If the `cookie` package isn't already a dependency in your store's `package.json`, install it by running `yarn add cookie` (or `npm install cookie`) in your repository root. This guide uses it to parse the request's cookie header safely.
2. In the `src/graphql/vtex/utils` directory, create a file named `auth.ts`. If the `utils` directory doesn't exist yet, create it first.
3. In the `auth.ts` file, add the following content:

```ts src/graphql/vtex/utils/auth.ts
import { UnauthorizedError } from '@faststore/api'
import { parse } from 'cookie'

/**
 * Returns the shopper's authentication token, or throws when the request
 * carries no valid session.
 */
export const getShopperToken = (ctx: any) => {
  const token = parse(ctx.headers?.cookie ?? '')[
    `VtexIdclientAutCookie_${ctx.account}`
  ]

  if (!token) {
    throw new UnauthorizedError('Authentication required')
  }

  return token
}
```

In this file, the following happens:

- `parse(ctx.headers?.cookie ?? '')` reads the raw `Cookie` header from the incoming request and parses it into a key-value object, using the `cookie` package rather than splitting the string manually. Token values can contain `=`, and a manual split can truncate one, which causes a silent `401` response later instead of a clear error here.
- `` `VtexIdclientAutCookie_${ctx.account}` `` is the name VTEX gives the shopper's session cookie for a given account, It's account-specific, which is why `ctx.account` is part of the key.
- If no token is found under that cookie name, `getShopperToken` throws `UnauthorizedError` immediately, rather than letting the resolver proceed with an empty or undefined token. `UnauthorizedError` comes from `@faststore/api` and results in a `401` response to the caller.

## Step 3: Creating the resolver

The type definitions from [Step 1](#step1---creating-the-type-definitions) tell your API that a `loyaltyBalance` query exists, but GraphQL still needs a function that actually produces the data when that query runs. This step writes that function: a resolver that uses the shopper's token from [Step 2](#step-2---creating-the-authentication-helper) to request the shopper's own record from Master Data, so the response is scoped to that one shopper instead of the whole `LoyaltyBalance` entity.

1. In the `src/graphql/vtex/resolvers` directory, create a file named `loyalty.ts`. If the `resolvers` directory doesn't exist yet, create it first.
2. In the `loyalty.ts` file, add the following content:

```ts src/graphql/vtex/resolvers/loyalty.ts
import { getShopperToken } from '../utils/auth'

const LoyaltyResolver = {
  Query: {
    loyaltyBalance: async (_: never, __: never, ctx: any) => {
      const token = getShopperToken(ctx)
      const { account } = ctx

      const searchParams = new URLSearchParams({
        _fields: 'availablePoints,nextExpirationDate',
      })

      const response = await fetch(
        `https://${account}.myvtex.com/api/io/safedata/LB/search?${searchParams}`,
        {
          headers: {
            Accept: 'application/vnd.vtex.ds.v10+json',
            'Content-Type': 'application/json',
            'Cache-Control': 'no-cache, no-store, must-revalidate',
            cookie: `VtexIdclientAutCookie_${account}=${token}`,
          },
        }
      )

      if (!response.ok) {
        throw new Error(`Loyalty balance request failed: ${response.status}`)
      }

      const documents = await response.json()

      if (!documents.length) {
        return { availablePoints: 0, nextExpirationDate: null }
      }

      return documents[0]
    },
  },
}

export default LoyaltyResolver
```

In this file, the following happens:

- `LoyaltyResolver.Query.loyaltyBalance` is the resolver function GraphQL calls whenever a `loyaltyBalance` query runs. Its third parameter, `ctx`, is the request context, the same object `getShopperToken` reads from in Step 2.
- `getShopperToken(ctx)` runs first and throws immediately if the shopper isn't signed in, so the rest of the function only ever runs for an authenticated shopper.
- `searchParams` builds the query string for the Master Data request, requesting only the two fields the account page needs (`availablePoints` and `nextExpirationDate`) via `_fields`.
- The `fetch` call sends the request to `io/safedata/LB/search`, `LB` is the `LoyaltyBalance` entity's acronym from **Context**. The `cookie` header rebuilds the shopper's session cookie from the account and token, which is what lets Master Data apply the entity's ACL to this specific shopper.
- If the response isn't successful (`!response.ok`), the resolver throws rather than returning partial or default data. See [Expected behavior](#expected-behavior) below for what this means in practice.
- If the shopper has no `LoyaltyBalance` document yet, `documents` is an empty array, and the resolver returns a default zero balance instead of `undefined`. Otherwise, it returns the first (and only) matching document.

Three details make this resolver return only the signed-in shopper's own data:

- The request goes to `io/safedata`, not `dataentities`. This endpoint applies the entity's ACL to the identity in the cookie, so it returns only the record that belongs to the signed-in shopper.
- The request carries the shopper's cookie instead of `appKey` and `appToken`. Application credentials would return any record in the entity, and the resolver would become responsible for filtering.
- `_fields` lists only the two fields the interface renders, which keeps the response small. The ACL, not the field list, is what prevents the resolver from ever seeing another shopper's document; `_fields` only avoids over-fetching data this component doesn't use.

### Expected behavior for empty and failed responses

This resolver can reach the `no balance to show` state through two different paths, and they mean different things:

- **No record yet:** `documents.length` is `0` and `response.ok` is `true`. This happens when the shopper hasn't earned points yet. The resolver returns `{ availablePoints: 0, nextExpirationDate: null }`, which is the expected, non-error case.
- **Authentication or ACL failure:** `response.ok` is `false` (for example, an expired token or an ACL misconfiguration), and the resolver throws. This is an error case, not a zero-balance case.

## Step 4: Registering the resolver

1. Open the `src/graphql/vtex/resolvers/index.ts` file. If your store doesn't have this file yet, create it in the `src/graphql/vtex/resolvers` directory.
2. At the top of the file, import the resolver you created in Step 3:

    ```ts
    import LoyaltyResolver from './loyalty'
    ```

3. Add `LoyaltyResolver` to the object exported by this file, so the FastStore API picks it up alongside any other resolvers:

    ```ts src/graphql/vtex/resolvers/index.ts
    import LoyaltyResolver from './loyalty'

    const resolvers = { ...LoyaltyResolver }

    export default resolvers
    ```

4. Save the file.

> ⚠️ This pattern assumes `LoyaltyResolver` is the only resolver contributing to the `Query` root in your store. If you already register other `Query` resolvers elsewhere, spreading them the same way overwrites rather than merges the `Query` object — merge the `Query` (and `Mutation`, if applicable) keys from each resolver file instead of spreading multiple resolver objects directly into `resolvers`.


## Step 5: Querying the data from a component

Declare the query in your custom component and render the result:

```tsx src/components/LoyaltyBalance.tsx
import { gql } from '@faststore/core/api'
import { useQuery_unstable as useQuery } from '@faststore/core/experimental'

const query = gql(`
  query LoyaltyBalanceQuery {
    loyaltyBalance {
      availablePoints
      nextExpirationDate
    }
  }
`)

export default function LoyaltyBalance() {
  const { data } = useQuery(query, {})

  if (!data?.loyaltyBalance) {
    return null
  }

  return (
    <p>
      You have {data.loyaltyBalance.availablePoints} points available.
    </p>
  )
}
```

> ⚠️ The `useQuery_unstable` hook is exported from `@faststore/core/experimental` and its API may change between releases. For the stable approach of extending an existing page query, see [Consuming API extensions](https://developers.vtex.com/docs/guides/faststore/api-extensions-consuming-api-extensions) and [Extending queries using fragments](https://developers.vtex.com/docs/guides/faststore/api-extensions-extending-queries-using-fragments).

Render this component only in a page that requires authentication. A signed-out visitor receives a `401` response, which the component treats as no data.

## Result

The account page displays the balance of the signed-in shopper. A shopper who is not signed in sees nothing, and no request can return the balance of another shopper, because the entity's ACL rejects it before your code runs.
